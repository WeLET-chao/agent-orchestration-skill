# Task Packet

Write one complete task packet before starting a non-trivial external-agent
session. Store it under the **task root**, normally
`.scratch/agent_prompts/<task>.md` (or under an external scratch tree when
`.scratch/` cannot be gitignored in-repo).

Use this structure, omitting sections that genuinely do not apply:

```markdown
# <Task title>

## Context
- Task class: impl | review | case-run
- Task root: <absolute path>
- Owning repository / case workspace
- Baseline ref (commit) for impl/review when applicable
- Case workspace: <path> (case-run)
- Shared framework / skill roots (read for commands/docs; must stay clean on case-run)
- For a continuation: current diff, accepted/provisional results, and active jobs
- Files/docs the agent must read
- Primary agent owns review and commits (impl)

## Objective And Hard Stop
- Concrete implementation, review, or case-run objective
- Hard stop: exact reviewable state where the agent must stop

## Execution And Supervision
- Log and final-report paths; expected artifacts
- Command, provider session, and process/tmux identifiers (filled at launch)
- Observable completion/failure signals and required exit status for headless runs
- Runtime/resource limits, concurrency caps, and bounded transient-retry conditions
- Pending jobs and remaining checks to preserve at handoff

## Problem And Diagnosis
- New capability: missing behavior and intended observable result
- Diagnostic task: observed failure, reproducer, and falsifiable hypotheses
- Correction task: established root cause and owning layer, with supporting evidence
- Rejected approaches and the evidence against them, when applicable
- Proposed route and the check that will test whether it addresses the problem

## Authority And Evidence
- Normative source and version/revision
- Corroborating implementation, if any
- Acceptance-only artifacts/cases
- Real verification environment and command
- Configuration-blocked stop condition

## Allowed Changes
- Exact paths or ownership area (write allowlist)
- review: only `.scratch/agent_artifacts/<task>/` (+ logs)
- case-run: only the case workspace + its `.scratch/`
- impl: only the assigned worktree

## Forbidden
- No commits or pushes
- No destructive git operations
- No unrelated refactors
- No fallback, repair, or case-specific heuristic as the main path
- No fabricated provider responses, domain artifacts, or expected values
- review/case-run: no mutating shared framework / primary tracked source
- case-run: no creating a framework-repo git worktree merely to hold the case
- case-run: no `pip install` / per-case `.venv` mutating a shared environment
- Do not treat provider `--add-dir` as a read-only boundary

## Implementation Requirements
- Required behavior and invariants
- Explicit failure behavior
- Artifact/provenance requirements
- Parallelism and resource constraints
- case-run: `PYTHONDONTWRITEBYTECODE` / `PYTHONPYCACHEPREFIX` guidance when using shared Python trees

## Verification
- Checks appropriate to the task type and changed behavior
- Reproducer and focused tests for a fix; real-tool/case acceptance when required
- Source/evidence verification for review; links/commands for documentation
- Render inspection for visual work; baseline comparison for visual improvement
- Negative/mutation check for a named correctness invariant when needed
- Exact task-local output paths
- case-run teardown: `git -C <shared-framework> diff --quiet` and clean `status --porcelain`
- case-run (paper-ls): also
  `check_case_run_acceptance.py --workspace … --final-report … --framework …`
  (hard-fail on path_selection / broken links / missing outcome)

## Final Report
- Files changed (impl) or artifacts written (review/case-run)
- Implemented behavior / review verdict / case outcome
- Commands and pass/fail counts
- Real artifacts and measurements
- Known issues/blockers
- Active jobs, unrun required checks, and evidence revision/artifact identity
- Confirmation that no forbidden fallback or commit was introduced
- case-run: confirmation shared framework remained clean
```

Expected values must not be generated by the implementation under test or
inferred from the acceptance case merely to make it pass. Synthetic fixtures
may test invariants but cannot satisfy a representative-case hard stop.

Do not invent a previous failure for feature work or present a diagnosis
hypothesis as a proved root cause. If the cause is unknown, delegate diagnosis
with a testable hypothesis and a concrete evidence deliverable. For a correction,
give the failed command/case, observed result, established cause or explicit
remaining uncertainty, requested change, and verification condition.
Do not repeat the same prompt
without new evidence or make each local failure a separate milestone. Once the
declared checks pass, finish the task unless a specific correctness issue remains.
If the original task premise changed materially, write a new complete packet
and use a clean session instead of stacking follow-up prompts. First preserve
the old work and evidence; identify accepted work to reuse and provisional work
to review or replace. Ordinary continuation reuses the assigned **task root** and
updates remaining work rather than repeating completed steps.
